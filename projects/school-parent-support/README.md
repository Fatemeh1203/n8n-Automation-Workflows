# سامانه پاسخگویی اولیا و چت‌بات معرفی مدرسه (n8n)

سامانه‌ی خودکارسازی برای یک مدرسه‌ی غیرانتفاعی (حدود ۴۰۰ دانش‌آموز) روی n8n، شامل چت‌بات تلگرامی
عمومی، احراز هویت اولیا، ثبت و پیگیری تیکت، اطلاعیه‌های مدرسه به ولی، ثبت غیبت روزانه و گزارش
هفتگی مدیریتی.

## قید سخت پروژه

- **بدون هوش مصنوعی.** تمام منطق بر پایه‌ی شرط (IF/Switch)، پرس‌وجوی جدولی SQL و زمان‌بندی
  (Schedule Trigger) است. هیچ نودی به مدل زبانی یا سرویس AI متصل نیست.
- **بدون سرویس خارجی به‌جز Bot API تلگرام.** پایگاه داده PostgreSQL روی سرور داخلی مدرسه
  اجرا می‌شود؛ n8n هم می‌تواند self-hosted روی همان زیرساخت باشد.
- تمام پیام‌های رو‌به‌کاربر و نام نودها فارسی هستند.

## ساختار مخزن

```
schema/schema.sql              طرحواره PostgreSQL (جدول‌های اصلی + جدول‌های زیرساختی)
workflows/
  01-ربات-تلگرام-مدرسه.json         جریان ۱ (منوی عمومی/FAQ) + احراز هویت + تیکت ولی + دستورات کارمند
  02-اطلاعیه-پنل-به-پایه-کلاس.json   جریان ۲: اطلاعیه از پنل مدرسه به پایه/کلاس
  03-غیبت-روزانه.json                جریان ۲: ثبت و اطلاع‌رسانی غیبت روزانه
  04-گزارش-هفتگی-مدیر.json           جریان ۲: گزارش هفتگی پنج‌شنبه ۱۸:۰۰
  99-مدیریت-خطای-مرکزی.json          گردش‌کار مشترک لاگ خطا + هشدار به مدیر
```

هر فایل JSON خروجی استاندارد n8n است و مستقیماً از منوی **Import from File** در n8n قابل
وارد کردن است.

## معماری: چرا یک ربات تلگرامی واحد؟

هر ربات تلگرام فقط یک Webhook فعال دارد؛ بنابراین امکان ساخت چند گردش‌کار مجزا که هرکدام یک
Telegram Trigger مستقل با همان توکن داشته باشند وجود ندارد (فقط آخرین وبهوک ثبت‌شده فعال می‌ماند).
به همین دلیل «جریان ۱» (منوی عمومی)، احراز هویت ولی، و تیکت ولی تأییدشده همگی در **یک** گردش‌کار
(`01-ربات-تلگرام-مدرسه`) با یک Telegram Trigger و مسیریابی داخلی بر اساس نقش کاربر (مهمان/ولی
تأییدشده/کارمند) پیاده‌سازی شده‌اند. جریان‌های مبتنی‌بر پنل مدرسه (اطلاعیه، غیبت) و زمان‌بندی
(گزارش هفتگی) چون از طریق Webhook/Schedule جدا فراخوانی می‌شوند، به‌صورت گردش‌کار مستقل ساخته شده‌اند
و برای ارسال پیام، همان نود Telegram (نه Trigger) را با یک credential مشترک صدا می‌زنند.

## جریان ۱ — عمومی (بدون احراز هویت)

در گردش‌کار `01-ربات-تلگرام-مدرسه`، شاخه‌ی «مهمان»:

- منوی inline: شهریه / ثبت‌نام / درباره‌ی مدرسه / آدرس و ساعت کاری / سؤال دیگر / من ولی هستم.
- پاسخ دکمه‌های منو از جدول `faq` بر اساس `menu_path` خوانده می‌شود.
- پیام آزاد (متن تایپ‌شده، نه دکمه) با نرمال‌سازی، روی `faq.keywords` جستجو می‌شود؛ در صورت
  عدم تطبیق، در `unanswered` ثبت و پیام عمومی نمایش داده می‌شود.
- «سؤال دیگر» → درخواست شماره → درخواست متن سؤال → ثبت در `leads` → پیام فوری به کارمند دسته‌ی
  «دفتر» (`staff.category = 'دفتر'`).
- «من ولی هستم / کد یکتا» → دریافت کد → تطبیق با `students.unique_code` → ثبت idempotent در
  `parents` (upsert بر پایه‌ی `UNIQUE(student_id, chat_id)`) → تأیید با تاریخ شمسی.

## جریان ولی تأییدشده (زیرساخت لازم برای «سامانه پاسخگویی اولیا»)

پس از احراز هویت، پیام‌های بعدی همان chat_id به‌عنوان «ولی تأییدشده» شناسایی می‌شود:

- منو: «ثبت تیکت جدید» → انتخاب دسته (آموزشی/مالی/اداری/فنی) → دریافت متن → ثبت **idempotent**
  تیکت (`ON CONFLICT (dedup_key)`؛ `dedup_key = chat_id:message_id` تلگرام) → اطلاع فوری به
  کارمند مسئول همان دسته (`staff.category`) → تأیید ثبت به ولی.
- کارمندان با دستورات متنی پاسخ می‌دهند:
  - `/reply <شماره تیکت> <متن پاسخ>` — `first_reply_at` را (فقط بار اول، با `COALESCE`) ثبت
    و پاسخ را برای ولی ارسال می‌کند.
  - `/close <شماره تیکت>` — تیکت را می‌بندد و به ولی اطلاع می‌دهد.
  - هر کارمند فقط می‌تواند تیکت‌های دسته‌ی خودش را ببندد/پاسخ دهد (`WHERE category = staffCategory`).

## جریان ۲ — مدرسه به ولی

- **اطلاعیه** (`02-اطلاعیه-پنل-به-پایه-کلاس`): Webhook از پنل مدرسه (`POST
  /webhook/school-panel/announcement` با بدنه‌ی `{grade, class, message}`؛ `class` اختیاری) →
  یافتن اولیای **تأییدشده** همان پایه/کلاس → ارسال حلقه‌ای پیام تلگرام → پاسخ JSON با تعداد گیرندگان.
- **غیبت روزانه** (`03-غیبت-روزانه`): Webhook از پنل (`POST /webhook/school-panel/absence` با
  بدنه‌ی `{uniqueCode, date}`؛ `date` اختیاری، پیش‌فرض امروز) → ثبت **idempotent** در `absences`
  (`UNIQUE(student_id, absence_date)`) → پیام همان‌روز به ولی تأییدشده با تاریخ شمسی.
- **گزارش هفتگی** (`04-گزارش-هفتگی-مدیر`): Schedule Trigger، پنج‌شنبه ساعت ۱۸:۰۰ به وقت
  `Asia/Tehran` → تعداد تیکت به تفکیک دسته (۷ روز اخیر)، میانگین زمان اولین پاسخ هر واحد (دقیقه)،
  تعداد تیکت‌های باز، پرتکرارترین موضوع → ارسال متن گزارش (با تاریخ شمسی) به کارمند دسته‌ی «مدیر».

## الزامات فنی و نحوه‌ی رعایت آن‌ها

| الزام | پیاده‌سازی |
|---|---|
| نرمال‌سازی فارسی قبل از هر تطبیق | تابع `normalizeFa` در ابتدای هر گردش‌کار: ی/ك عربی → ی/ک فارسی، نیم‌فاصله/ZWNJ → فاصله، اعداد فارسی/عربی → لاتین، فشرده‌سازی فاصله‌ها |
| تاریخ شمسی در خروجی کاربر؛ ذخیره UTC | ستون‌های `TIMESTAMPTZ` (UTC) در دیتابیس؛ تابع `toJalali` (الگوریتم استاندارد بدون کتابخانه خارجی) فقط هنگام نمایش پیام به کاربر اجرا می‌شود |
| idempotent بودن هر تیکت | `tickets.dedup_key UNIQUE` = `chat_id:message_id` تلگرام + `ON CONFLICT DO UPDATE` بی‌اثر؛ همین الگو برای `parents` (کد یکتا) و `absences` (غیبت روزانه) نیز اعمال شده |
| بدون افشای داده‌ی دانش‌آموز بدون `verified_at` | تمام پرس‌وجوهای مرتبط با ولی، شرط `verified_at IS NOT NULL` دارند؛ جدول `parents` بدون این شرط هرگز join نمی‌شود |
| لاگ خطای هر نود + پیام عمومی به کاربر | گردش‌کار `99-مدیریت-خطای-مرکزی` (Error Trigger) باید به‌عنوان **Error Workflow** روی هر ۴ گردش‌کار دیگر تنظیم شود؛ خطا در جدول `logs` ثبت و به مدیر هشدار داده می‌شود؛ پیام‌های کاربر همیشه عمومی و بدون جزئیات فنی هستند |

## راه‌اندازی

1. **پایگاه داده**: `schema/schema.sql` را روی یک PostgreSQL داخلی اجرا کنید و حداقل یک ردیف
   `staff` با `category = 'دفتر'` و یک ردیف با `category = 'مدیر'` وارد کنید (نمونه در انتهای فایل).
2. **ربات تلگرام**: یک بات از طریق [@BotFather](https://t.me/BotFather) بسازید و توکن آن را در
   یک Credential از نوع Telegram API با نام «ربات تلگرام مدرسه» در n8n ثبت کنید.
3. **دیتابیس در n8n**: یک Credential از نوع Postgres با نام «دیتابیس داخلی مدرسه» بسازید و به
   سرور داخلی مدرسه وصل کنید.
4. هر ۵ فایل داخل `workflows/` را در n8n وارد (Import) کنید. در هر نود Postgres/Telegram که
   credential را خالی یا `__SET_ME__` می‌بینید، credential واقعی را انتخاب کنید (n8n معمولاً
   امکان «Set for all nodes of this type» را می‌دهد).
5. گردش‌کار `99-مدیریت-خطای-مرکزی` را Publish/Activate کنید، سپس در تنظیمات هر یک از ۴ گردش‌کار
   دیگر (Settings → Error Workflow) همین گردش‌کار را انتخاب کنید.
6. گردش‌کار `04-گزارش-هفتگی-مدیر` را بررسی کنید که منطقه‌ی زمانی آن `Asia/Tehran` است (از قبل
   در فایل تنظیم شده).
7. آدرس‌های Webhook پنل مدرسه را برای تیم فنی پنل مستند کنید:
   - اطلاعیه: `POST {n8n-base-url}/webhook/school-panel/announcement`
   - غیبت روزانه: `POST {n8n-base-url}/webhook/school-panel/absence`
8. هر ۴ گردش‌کار عملیاتی (۰۱ تا ۰۴) را پس از تست Activate کنید.

## نکات توسعه‌ی بعدی (خارج از دامنه‌ی فعلی)

- نمایش «وضعیت تیکت‌های من» برای ولی تأییدشده (با همان الگوی نشست/session قابل افزودن است).
- ثبت امتیاز (`tickets.rating`) از سوی ولی پس از بسته‌شدن تیکت.
- پنل مدیریتی FAQ برای ویرایش بدون دسترسی مستقیم به دیتابیس.
