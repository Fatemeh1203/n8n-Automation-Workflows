## تصمیم معماری: یک بات مشترک برای هر دو جریان

برای این نمونه یک بات تلگرام مشترک بین جریان ۱ (عمومی) و جریان ۲ (اولیا) استفاده می‌شود —
دو جریان، هرکدام با ردیف `bot_offset` خودشان (`'flow1'` و `'flow2'`)، به‌طور مستقل همان بات را
poll می‌کنند. تلگرام به هر poller اجازه می‌دهد offset خودش را جدا نگه دارد، پس تداخلی در
سطح API پیش نمی‌آید. تفکیک مسیر بر عهده‌ی منطق هر جریان است:

- **جریان ۱ (عمومی)** فقط به تپ‌شدن دکمه‌های منوی FAQ یا کلیک روی «سؤال دیگر» واکنش نشان
  می‌دهد.
- **جریان ۲ (اولیا)** فقط به `chat_id`ای واکنش نشان می‌دهد که قبلاً در `parents` ثبت شده
  (حتی بدون تأیید)، یا به پیامی که با دستور `/parent` شروع شده باشد — این دستور، ورودی
  رسمی به بخش اولیاست.
- پیامی که هیچ‌کدام از این دو شرط را ندارد، توسط جریان ۱ به‌عنوان پیام بی‌پاسخ ثبت می‌شود.

اگر مدرسه دو بات جدا (یکی برای معرفی، یکی برای اولیا) ترجیح دهد، فقط لازم است
`TELEGRAM_BOT_TOKEN` در تنظیمات هر Workflow جدا شود — منطق داخلی جریان‌ها تغییری نیاز ندارد.

## جدول‌ها

۷ جدول دامنه (طبق بریف: `students`, `parents`, `tickets`, `staff`, `faq`, `leads`,
`unanswered`) + ۴ جدول عملیاتی که برای پیاده‌سازیِ خواسته‌های خودِ بریف لازم بودند
(`bot_offset` برای polling با offset، `verification_attempts` برای قفل ۳-بار-خطا،
`sla_alerts` برای «فقط یک یادآوری در هر آستانه»، `error_log` برای مدیریت خطا) — همه در
`.claude/rules/db-schema.md` مستند شده‌اند و در `sql/schema.sql` نوشته شده‌اند و روی
PostgreSQL واقعی تست اجرا شده‌اند.

## سؤالات باز (پاسخ‌داده‌نشده در این نمونه)

- **first_reply_at**: بریف مشخص نکرده کارکنان چطور به تیکت پاسخ می‌دهند (چت جدا؟ پنل؟).
  برای این نمونه فرض شده کارمند پس از پاسخ‌دادن (به‌صورت دستی، خارج از این سیستم) دکمه‌ی
  «پاسخ داده شد» را در همان پیام اطلاع‌رسانی تیکت می‌زند — این دکمه `tickets.first_reply_at`
  را پر می‌کند. برای استقرار واقعی این فرض باید با مدرسه تأیید شود.
- **پنل اطلاعیه/غیبت (Flow 3)**: در این نمونه با n8n Form Trigger پیاده شده (بدون دامنه/SSL
  اضافه) — اگر مدرسه یک پنل ادمین واقعی بخواهد، آن یک پروژه‌ی جدا و بزرگ‌تر است.
